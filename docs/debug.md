# Игровая страница и отладка

`/` — тестовый игровой интерфейс. На нём есть чат игрока (`first`), ответы
ведущего (`second`), броски костей и вкладка персонажей с инвентарём.
`/debug` и `/debug/` — административный интерфейс отладки этой же комнаты.
На нём есть инспектор внутренних сущностей, JSON-заглушка и полный журнал событий.
Ведущего пока заменяют ручные команды JSON-заглушки.

Переходы в шапке сохраняют `#room=…&access=…`. «Скопировать ссылку» копирует
адрес текущего представления вместе с комнатой и ключом. Кнопка `+` создаёт
новую комнату на текущей странице. Два представления можно открыть в разных
окнах: они используют ту же SQLite, а новые события и состояние обновляются
через HTTP. Отправка команд ведущего, повтор без дублирования и броски костей
используют существующие API. Разделение страниц не меняет эти контракты.

## Внутренние сущности

Инспектор показывает JSON выбранной группы:

- `room`: ID комнаты и время создания;
- `players`: игроки и их ID;
- `characters`: персонажи игроков и NPC, владельцы, атрибуты и вычисленные показатели;
- `items`: предметы с `character_id`, количеством, расположением и хватом;
- `rules`: сохранённый конфиг инвентаря комнаты;
- `subscribers`: зарегистрированные подписчики `first` и `second`;
- `tools`: описание инструмента костей и контракт команд ведущего.

Показываются ревизия реестра, курсор очереди и количество сущностей и событий.
Инспектор не редактирует сущности. Изменения инвентаря выполняются на игровой
странице. Для комнаты без реестра первое чтение создаёт его с начальной
ревизией и сохраняет текущий конфиг правил, как обычное чтение `/roster`.

## Полный журнал

Журнал содержит `chat.message`, `tool.offer`, `tool.call` и `tool.result`.
Каждая запись сохраняет ID, `request_id`, автора, время, видимость, текст,
metadata и остальные поля исходного JSON. Это полный административный просмотр,
поэтому сюда входят и события, доступные только `first` или только `second`.
Собственная лента JSON-заглушки остаётся фильтрованной по `second`.

Поиск работает по всем полям JSON уже загруженных записей; дополнительно можно
выбрать тип события и представление подписчика. Фильтр подписчика лишь меняет
отображение полного журнала в браузере. Новая история загружается порциями
по 200 событий до конца очереди, затем подгружаются новые записи. Дубликаты
страниц и повторные запросы не дублируют строки. Автопрокрутка следует за новыми
событиями, если включена и пользователь находится у конца списка.

## HTTP API

`GET /api/rooms/{room_id}/debug?after=0` возвращает:

```json
{
  "room": {"id": "UUID", "created_at": "…"},
  "revision": 0,
  "entities": {
    "room": {"id": "UUID", "created_at": "…"},
    "players": [], "characters": [], "items": [],
    "rules": {}, "subscribers": [], "tools": {}
  },
  "queue_counts": {"chat.message": 2},
  "queue": {
    "messages": [], "next_cursor": 0, "has_more": false
  }
}
```

`after` — неотрицательный целочисленный ID последнего события. Предел и семантика
курсора совпадают с API сообщений: ID глобальны для базы, пропуски допустимы,
но в ответ попадают только события выбранной комнаты. `queue_counts` считает
все события комнаты по типам независимо от текущей страницы.
Метаданные и страница очереди читаются в одной транзакции; реестр читается
отдельным согласованным снимком со своей ревизией. Повторное чтение не создаёт
событий чата и не меняет ревизию существующего реестра.

Некорректный курсор даёт 400, отсутствующая комната — 404. На сервере с ключом
запрос требует тот же Bearer-токен, что и остальные API; без него — 401.
Статические HTML-оболочки страниц доступны без ключа, данные — через защищённые API.
Сервер не предоставляет SQL, пути к базе, ключи доступа или другие локальные
файлы через инспектор.

Пока приложение остаётся общим административным стендом: любой обладатель
ключа может открыть обе страницы и полный журнал. Раздельные права игроков
и ведущего потребуют отдельной модели авторизации.
