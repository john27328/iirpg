# Общая очередь сообщений

Каждая комната содержит один упорядоченный журнал. `Chat` публикует в него
JSON-записи и читает свою выборку. Чаты не хранят ссылок друг на друга.
Чтение не удаляет записи; у каждого представления собственный курсор.

## Формат записи

```json
{
  "id": 42,
  "room_id": "f5b6b241-12fd-449f-926b-bf4df8227b96",
  "request_id": "2269de71-e2e6-4685-9872-b7739fa18e7d",
  "schema_version": 1,
  "sender": "first",
  "type": "chat.message",
  "text": "Заметка для первого чата",
  "choices": [],
  "visibility": {"mode": "selected", "chat_ids": ["first"]},
  "metadata": {"scene_id": "tavern", "tags": ["note"]},
  "created_at": "2026-10-27T16:00:00.000+00:00"
}
```

`id` назначает хранилище; это порядок записи в журнал, а не время на клиенте.
`request_id` задаёт клиент для безопасного повтора отправки. Повтор с тем же
содержимым возвращает исходную запись; изменение текста, вариантов, видимости или metadata
с тем же идентификатором возвращает `409`.

`visibility.mode`:

- `all`: сообщение видно всем чатам комнаты; `chat_ids` пуст.
- `selected`: сообщение видно только перечисленным чатам. Сейчас существуют
  `first` и `second`. Пустой список и неизвестные чаты запрещены.

Автор не получает видимость автоматически: он должен входить в список,
если хочет видеть запись в своей ленте. Слева интерфейс показывает обычный
чат `first`, справа — JSON-заглушку, читающую выборку `second`. Чат предлагает
общий доступ и заметку только для себя. В JSON-редакторе можно указать любой
допустимый список. Скрытые от `second` записи в JSON-инспектор не попадают.

`metadata` — объект JSON до 4096 байт для дополнительного контекста.
Он не меняет права доступа. Поддерживаемый тип сейчас — `chat.message`;
новые типы нужно вводить вместе с валидацией и обработчиками.

`choices` — необязательный массив до 10 непустых строк по 200 символов.
Порядок и текст вариантов сохраняются. Отсутствующее поле означает `[]`,
включая старые записи очереди. Во входящем сообщении чата варианты показываются
кнопками: нажатие сразу отправляет выбранный текст. Собственный ответ можно
отправить через поле ввода; нажатие варианта сохраняет имеющийся черновик.
В JSON-инспекторе поле выводится
в составе записи. Варианты имеют ту же видимость, что и само сообщение.

## API

- `POST /api/rooms/{room_id}/messages`: передать `sender`, `text`, `request_id`;
  опционально `type`, `visibility`, `metadata`, `choices`.
- `GET /api/rooms/{room_id}/messages?chat=first&after=0`: прочитать страницу
  указанного подписчика. `chat` обязателен.

JSON-редактор передаёт введённое тело запроса без пересборки. Обязательные поля
нужно задать в нём явно. `text` сохраняет пробелы и переводы строк; пустой или
полностью пробельный текст запрещён, предел — 2000 символов вместе с пробелами.
Сервер назначает `id`, `room_id`, `created_at` и `schema_version` самостоятельно.
Форматирование самого JSON при хранении и выводе может измениться.

Ответ чтения: `messages`, `next_cursor`, `has_more`. Сервер просматривает
до 200 записей очереди и возвращает только видимые. Даже пустая выборка может
продвинуть `next_cursor` и иметь `has_more=true`: клиент должен продолжить чтение
с новым курсором, чтобы пройти скрытые сообщения. Последующие чтения другого
чата независимы.

В SQLite JSON хранится в `queue_events.envelope`; поля порядка, комнаты
и повтора запроса индексируются отдельно. Общий JSON-файл не используется,
чтобы не перезаписывать его целиком при каждом параллельном запросе.

## Граница доступа

Оба представления принадлежат одному административному стенду и используют
общий ключ сервера. Фильтрация выполняется сервером, но параметр `chat` не является
авторизацией пользователя. Для игроков с разными правами сервер должен определять
подписчика из авторизованной сессии и проверять доступ к комнате.
