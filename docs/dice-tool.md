# Инструмент dice.roll

Универсальный движок получает формат броска, формулу и критерий успеха.
Он возвращает значения всех костей, числовой `result` и булев `success`.
Расчёт выполняет Python; чат показывает итог как обычную проверку ведущего.
ИИ сможет вызывать этот же инструмент структурированным запросом.

Для ИИ и обычных проверок в заглушке используется короткий формат
[команд ведущего](gm-commands.md): `offer_roll` и `roll` с полями `roll` и `target`.
Он не требует служебных UUID, отправителя и полного `tool.call`.
Примеры полных событий ниже предназначены для режима «Сырой JSON очереди».

## Форматы в правилах

Единственный источник форматов: `src/iirpg/rules/dice_systems.json`.
Файл поставляется вместе с пакетом. Для другого файла:

```bash
PYTHONPATH=src python3 -m iirpg --dice-rules /path/to/dice_systems.json
```

Каждый формат содержит `label`, `aggregation`, `roll` и `success`.
`sum` суммирует значения костей; `count` считает кости, удовлетворяющие
`success.die`. Целый модификатор применяется к итоговому числу.
Встроены общие форматы `d20`, `sum_d6`, `percentile`, `pool_d10`.
Это исходные примеры форматов, без правил конкретных игровых изданий.

Пример авторского формата в объекте `systems`:

```json
{
  "custom_pool": {
    "label": "Мой пул",
    "aggregation": "count",
    "roll": "5d10",
    "success": {
      "operator": ">=",
      "target": 3,
      "die": {"operator": ">=", "target": 6}
    }
  }
}
```

В корне файла нужны `version: 1` и `systems`. После изменения перезапустите
сервер; каталог форматов и форма чата загрузят новые значения.
При добавлении конкретной редакции Pathfinder или «Маскарада» сохраняйте
источники правил и применимые уведомления. Особые механики вроде критических
комбинаций добавляются отдельной стратегией движка, её параметры — в правилах.

## Сырой вызов со стороны будущего ИИ

JSON-заглушка `second` заменяет ИИ-ведущего: введённый JSON отправляется
как тело HTTP-запроса, без пересборки. Подключать модель для этой проверки не нужно.

### Предложить проверку игроку

Обычный сценарий ведущего — предложить проверку и дождаться, пока игрок
сам нажмёт «Бросить кости». Кнопка «Предложить бросок» в заглушке заполняет пример:

```json
{
  "sender": "second",
  "type": "tool.offer",
  "tool": "dice.roll",
  "recipient": "first",
  "request_id": "6309dba7-9700-4f47-8c13-056836bdc06c",
  "text": "Чтобы незаметно пройти мимо стражи, проверьте скрытность.",
  "arguments": {
    "system": "d20",
    "roll": "1d20+5",
    "success": {"operator": ">=", "target": 15},
    "label": "Скрытность"
  }
}
```

Предложение отправляется в `POST /api/rooms/{room_id}/messages` и сохраняется
как `tool.offer`. Оно не запускает генератор случайных чисел. `recipient`
должен быть другим известным участником и входить в видимость предложения.
Сервер проверяет аргументы заранее и возвращает в записи `roll_request_id`.

При нажатии игрок отправляет в тот же API:

```json
{
  "sender": "first",
  "type": "tool.call",
  "tool": "dice.roll",
  "request_id": "ЗНАЧЕНИЕ_roll_request_id_ИЗ_ПРЕДЛОЖЕНИЯ",
  "offer_id": "6309dba7-9700-4f47-8c13-056836bdc06c"
}
```

В `POST /api/rooms/{room_id}/tools/dice` поля `type` и `tool` можно опустить.
Параметры, видимость и metadata берутся из сохранённого предложения этой комнаты.
Передать другие значения запрещено. `sender` должен совпадать с `recipient`.
Это проверка участника прототипа; общий ключ стенда по-прежнему даёт доступ
к обоим представлениям и не является личной авторизацией игрока.

Для предложения сервер вычисляет `roll_request_id` как UUIDv5 в пространстве
UUID предложения с именем `dice.offer.accept`. При принятии нужен именно этот
идентификатор: все окна используют один ID, поэтому проверка выполняется один раз.
Для повторного броска ведущий создаёт новое предложение с новым `request_id`.
Ожидающие предложения и выполненные результаты сохраняются после перезапуска.

В JSON-истории остаются три записи: предложение, вызов игрока и результат.
Вызов и результат содержат `offer_id` и `offered_by`; результат также содержит
`requested_by` с игроком и `tool_call_id` со ссылкой на вызов игрока.
Чат объединяет три записи в одну карточку с описанием и результатом.
Черновик игрока и настройки самостоятельного броска при нажатии сохраняются.

### Выполнить бросок сразу

Минимальный пример для редактора (также доступен по кнопке «Пример костей»):

```json
{
  "sender": "second",
  "type": "tool.call",
  "tool": "dice.roll",
  "request_id": "b9e140f0-74ef-4874-a6a6-82a7e15eeec8",
  "arguments": {
    "system": "d20",
    "roll": "1d20+5",
    "success": {"operator": ">=", "target": 15}
  }
}
```

Отправьте его и проверьте две записи в истории: запрос от `second` и ответ
от `dice`. Без `visibility` обе записи доступны обоим представлениям;
без `metadata` применяется `{}`. Повтор того же JSON возвращает прежний
ответ и не добавляет записей. Для новой проверки нажмите «Новый request_id».

## Вызов через JSON-заглушку

Кнопка «Пример костей» заполняет готовый вызов. Его можно отправить в обычный
`POST /api/rooms/{room_id}/messages`:

```json
{
  "sender": "second",
  "type": "tool.call",
  "tool": "dice.roll",
  "request_id": "2269de71-e2e6-4685-9872-b7739fa18e7d",
  "arguments": {
    "system": "d20",
    "roll": "1d20+5",
    "success": {"operator": ">=", "target": 15},
    "label": "Скрытность"
  },
  "visibility": {"mode": "all", "chat_ids": []},
  "metadata": {}
}
```

`system` выбирает формат из правил. `roll` можно опустить для формулы по
умолчанию. `success` обязателен; для пула `success.die` можно опустить,
тогда применяется условие на кости из правил. `label` необязателен.
Операторы: `>=`, `>`, `<=`, `<`, `==`, `!=`. Например, процентная проверка
может требовать `result <= 50`, а пул — не менее трёх костей со значением ≥ 6.

Формулы поддерживают `NdM`, несколько групп и целые модификаторы:
`d20+5`, `2d6`, `2d6+1d4-2`. Пределы: 120 символов, 12 слагаемых,
100 костей суммарно, 2–10000 граней и модификатор ±10000.
Порог — целое число в пределах ±1000000. Отрицательная группа вычитает
сумму либо число успешных костей этой группы.

## API для ведущего

- `GET /api/tools/dice`: описание инструмента, JSON Schema его аргументов
  и текущие форматы из правил.
- `POST /api/rooms/{room_id}/tools/dice`: передать `sender`, `request_id`,
  `arguments`, опционально `visibility` и `metadata`. Это тот же вызов,
  что `tool.call` в очереди, с тем же пространством идентификаторов.

Оба пути отправки возвращают `message`, числовой `result` и булев `success`.
В `message.tool_result` находятся формула, отдельные броски, модификатор,
агрегация, критерий и человекочитаемый `summary`. Например, при выпадении
13 на `1d20+5` и пороге ≥ 15 результат равен 18, успех — `true`.

В очереди атомарно сохраняются две последовательные записи:

- `tool.call`: исходный `sender`, клиентский `request_id`, нормализованные
  `arguments` и текст с формулой и условием успеха.
- `tool.result`: `sender: "dice"`, `requested_by` с автором вызова,
  нормализованные `arguments`, `tool_result` и `tool_call_id`, равный `request_id` вызова.

У ответа собственные `id` и `request_id`; последний сервер вычисляет как
UUIDv5 с пространством UUID вызова и именем `tool.result`. HTTP-ответ по-прежнему
возвращает результат в `message`; обе записи доступны через чтение истории.
Обе записи наследуют видимость и metadata вызова; фильтрация применяется к обеим.
Клиент не может отправить готовый `tool.result` от имени инструмента.

## Сохранение и повторы

`request_id` относится к одной проверке. SQLite блокирует создание записи
на время короткого локального броска и сохраняет запрос вместе с результатом атомарно.
Параллельные повторы и повтор после перезапуска возвращают сохранённую запись
без нового вызова генератора. Изменение аргументов, автора, видимости или
metadata с прежним ID даёт `409`; для новой проверки нужен новый ID.
Изменение формата в файле правил также может изменить нормализованные аргументы.
Броски, сохранённые до появления пары запрос–ответ, остаются прежними одиночными
результатами; их повтор возвращает старую запись без переброса и дополнения истории.

Генератор получает только число граней. По умолчанию используется `secrets`;
в тестах подставляется детерминированная функция. Ошибка генератора не оставляет
частично записанного события. Здесь нет обращений к внешним ИИ API.
