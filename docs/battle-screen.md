# Экран боя

`/battle` — отдельное представление той же комнаты. Оно показывает карту,
очередь инициативы, активного персонажа и его игрока, доступные действия,
текстовый ввод, журнал и намерения. Страница игры остаётся местом подготовки
карты, персонажей и инвентаря. Во время активного боя её действия сцены
блокируются; ссылка ведёт на экран боя. Навигация сохраняет room/access в
URL-фрагменте, как и остальные страницы. Общая авторизация стенда не менялась.

## Заготовки боя

Перед началом доступны «Дуэль в таверне», «Патруль в лесном лагере»,
«Группа в таверне» и «Текущая сцена · свой бой». Заготовки задаются в
`rules/battle_presets.json`: ID, название, описание, `map_template`, `group_id`.
Каталог доступен через `GET /api/combat/presets` с обычным ключом комнаты.

Выбор только показывает описание и фиксирует состав противников. Карта
заменяется при нажатии «Начать бой»; её объекты сбрасываются, ожидающие
намерения сцены отменяются, персонажи расставляются заново. Загрузка карты
и начало боя выполняются в одной транзакции. При ошибке героев, ID заготовки
или несовпадении группы текущая сцена и бой не меняются. Повтор с тем же ID
возвращает прежний результат без перезагрузки карты. Во время боя выбор
заблокирован. Режим своей сцены сохраняет подготовленную карту и объекты.
Новой комнате без карты по умолчанию предлагается дуэль, чтобы начать бой
без отдельного посещения редактора сцены.

Пример:

```json
{"action":"start","revision":0,"character_ids":["HERO_UUID"],"preset_id":"forest_patrol"}
```

`group_id` можно опустить; при его передаче он должен совпадать с заготовкой.
В состоянии сохраняются `preset_id`, `preset_name`, а стартовое событие
содержит ID заготовки и сцену до/после загрузки. Настройки читаются при старте
сервера. Существующие API без `preset_id` работают по прежней схеме.

## Группа героев

Выберите от одного до четырёх персонажей типа PC с положительными текущими
ОЗ. Затем выберите группу противников и начните бой. У каждого героя отдельные
инициатива, ОЗ, щит, позиция и очередь. Стартовые клетки не пересекаются:
при совпадении позиций дополнительные герои размещаются на свободном полу
рядом с первым. Стартовые позиции врагов выбираются с учётом геометрии и
занятых клеток; при движении живые участники блокируют путь.

Очередь определяет текущего героя, выбирать его в обход инициативы нельзя.
Карточка показывает его имя, ОЗ, КБ, бонусы и оставшиеся действия. Если в
реестре указан игрок-владелец, отображается его имя; иначе — управление всей
группой. Это отображение владельца в общем стенде, не отдельная система входа
или разграничения прав между несколькими пользователями.

Клик по карте выбирает клетку назначения, цель или объект. Для исполнения
нужна соответствующая кнопка. Союзная фишка позволяет посмотреть участника,
не передаёт ему ход. Масштаб карты меняется отдельно; широкая карта и очередь
прокручиваются внутри своих областей. При смене участника очередь показывает
его карточку без прокрутки всей страницы.

Панель разделена на «Без указания цели» и действия для выбранной клетки.
Без выбора показаны только применимые общие действия: ещё не поднятый щит
при наличии действий и конец хода. Выбор клетки не назначает цель
автоматически в другом месте карты: союзная клетка не предлагает удара,
далёкая цель — атаки, недоступный путь — перемещения. Объект предлагает
только разрешённые сейчас опрокидывание/укрытие. После изменения состояния
список пересчитывается; при нуле действий остаётся конец хода. Выбор можно
снять. Для старого боя без карты остаётся отдельный явный выбор цели.

Доступность вычисляет движок по одной согласованной версии боя и сцены:

```text
GET /api/rooms/{room}/combat/actions?revision=N
GET /api/rooms/{room}/combat/actions?revision=N&x=3&y=4
```

Для боя без карты вместо x/y можно передать `target_id`. Ответ содержит
`general`, `selected`, `actor_id`, `revision`, `scene_revision` и описание
выбора; у каждого пункта — название, стоимость и готовая команда. Цена
перемещения включает реальный путь, трудную местность и занятые клетки.
Проверки досягаемости, укрытия, движения и опрокидывания общие с исполнением.
Запрос не бросает кости, не меняет бой, сцену или журнал и не вызывает ИИ.
При устаревшей ревизии возвращается 409. Интерфейс отбрасывает запоздавшие
ответы для прежнего выбора и повторно проверяет команду при исполнении.

В ход NPC доступны одно решение ИИ и весь ход обычного алгоритма. Автоматического
вызова модели нет. При нуле действий кнопка заканчивает ход без обращения к
модели. Настройки провайдера и подробные контексты доступны через отладку.

## Текстовые действия

Короткие команды разбираются сервером без обращения к языковой модели:

- `удар`, `атаковать`, `атакую`, `ударить` — по выбранной цели;
- `атакую Старший патруля`, `удар по Старший патруля` — по точному имени;
- `щит`, `поднять щит`, `поднимаю щит`;
- `идти 3,4`, `иду [3,4]`, `переместиться 3 4`;
- `укрытие`, `укрыться`, `занять укрытие` — у выбранного объекта;
- `опрокинуть`, `опрокидываю` — выбранный объект;
- `опрокинуть Тяжёлый стол` — объект по точному имени;
- `конец хода`, `закончить ход`, `заканчиваю ход`.

Опрокидывание использует существующий пример сцены: соседний объект в той
же зоне, Атлетика из листа и настроенная КС. Оно стоит действие независимо
от успеха. Это авторский пример разрешения, не универсальное действие PF2e.
Объект и состояние бойца сохраняются в одной транзакции с броском и журналом.

Любой другой текст, включая составные фразы «поднять щит и атаковать»,
сохраняется как `pending`-намерение. Ничего не выполняется частично, действия
не списываются и NPC не получают намерение как физическое событие в своей
памяти. В панели ведущего его можно отклонить или разрешить как один из
реализованных шагов: удар, щит, перемещение, укрытие, опрокидывание или конец
хода. Исполнение разрешено только в активный ход автора, со всеми обычными
проверками цели, позиции, ресурсов и ревизии. Для составного замысла нужны
отдельные решения/намерения; неизвестные эффекты ещё не исполняются ИИ-мастером.

Текстовый черновик закрепляется за героем при вводе. Если другая вкладка
закончила его ход, поле сохраняется, но отправить его от нового героя нельзя:
нужно дождаться хода автора либо очистить черновик. Клетка назначения и выбор
цели при смене активного участника сбрасываются.

## Журнал

`journal` — компактные записи текущего столкновения: стабильный ID, тип,
автор, цель, раунд, время, текст, исходная текстовая команда и ID намерения.
Полные before/after-события по-прежнему хранятся в общей очереди для отладки.
Журнал обновляется вместе с ревизией боя и не дублируется при повторах.
Старые сохранения с одним `log` отображаются без миграции. Переключатель
«Следить» управляет автоматической прокруткой; ручная позиция сохраняется
при появлении новых событий, если слежение выключено.

## API

Все действия остаются в `POST /api/rooms/{room}/combat` с UUID
`Idempotency-Key`. Группа вместо одиночного персонажа:

```json
{"action":"start","revision":0,"character_ids":["HERO_1_UUID","HERO_2_UUID"],"group_id":"patrol"}
```

Старый `character_id` поддерживается. Одновременно обе формы передавать
нельзя. В обычные команды можно передавать `actor_id`; при несовпадении с
активным entity_id сервер отклоняет команду. Экран всегда передаёт этот ID:

```json
{"action":"intent","revision":5,"actor_id":"HERO_UUID","text":"Поднять щит"}
```

Для кратких команд по выбранной цели/объекту используется `target_id`.
Ответ — прежнее состояние столкновения с `journal`, `intents` и данными
игрока-владельца у героев. Произвольное намерение:

```json
{"action":"intent","revision":6,"actor_id":"HERO_UUID","text":"Отвлеку противника разговором"}
```

Решение ведущего:

```json
{"action":"resolve_intent","revision":7,"actor_id":"HERO_UUID","intent_id":"INTENT_UUID","effect":"shield"}
```

Другие `effect`: `strike`, `move`, `take_cover`, `tip_over`, `end_turn`,
`reject_intent`. Для цели/клетки передаются обычные `target_id`/`position`.
Решённое или отклонённое намерение нельзя применить повторно. Повтор той же
операции возвращает старую квитанцию без повторного броска или расхода действия;
актуальное состояние нужно читать отдельно, если другие участники уже ходили.

Бой и намерения сохраняются на сервере. Черновик текста хранится только в
памяти текущей вкладки; после перезагрузки не восстанавливается. При сетевой
ошибке повтор запроса выполняется явно кнопкой проверки результата с тем же
ID; автоматически новые команды или обращения к ИИ не создаются.

## Проверка

Быстрые тесты покрывают группу, смену автора, дружественные цели, изоляцию
комнаты, известные и составные текстовые команды, отказ без изменения боя,
опрокидывание, намерения и повторное разрешение. Процессная release-проверка
перезапускает сервер между намерением и следующим ходом, проверяет карту,
очередь, журнал и старую квитанцию. Браузерный прогон с заглушкой ИИ проверяет
полный бой группы, текст, ручное решение, внешнюю смену хода с черновиком,
сохранение журнала, навигацию с ключом и мобильный экран.

## Разбор намерений ИИ-мастером

Свободный текст, который не распознан как точная команда, сохраняется без
расхода действий. Экран автоматически отправляет один запрос на
`POST /api/rooms/{room}/ai/gm/intent` с `revision`, `intent_id` и необязательным
`target_id`. Старые намерения можно разобрать кнопкой «Разобрать ИИ».
Мастер получает отдельный контекст `role: gm`: намерение, активного героя,
цели и конечный набор реализуемых вариантов. Чаты в этот контекст не входят.
Контекст NPC остаётся ограниченным его наблюдениями; испуг и замеченные
признаки испуга доступны ему без раскрытия чужих числовых характеристик.

Модель выбирает вариант и краткое объяснение. Цена, модификатор и КС
проверяются движком, сохраняются в `intent.analysis` и попадают в журнал.
Это ещё не бросок: `accept_intent` повторно проверяет возможность действия,
проводит проверку и расходует ресурс. ИИ не вызывается при подтверждении.
Запросы идемпотентны; автоматических повторов внешнего вызова при ошибках нет.
При неподдерживаемой механике намерение остаётся для ручного решения.

`demoralize_pf2e.json` задаёт Деморализацию: одно действие, Запугивание
против КС Воли в пределах 30 футов; успех даёт Испуган 1, критический успех — 2.
Крик и грохот без понятных слов получают штраф −4, а не бесплатное особое
визуальное умение. Учитываются слух цели и невосприимчивости fear/mental/emotion.
Повторная попытка того же участника запрещена 10 минут вне зависимости от
исхода. В учебной симуляции это 100 раундов текущего боя; новый бой создаёт
новых учебных противников. Дистанции и слышимость используют пространственный
прототип с ортогональной сеткой, а не полную систему обнаружения PF2e.

Испуг уменьшает реализованные проверки и КС: атаки, КБ, Волю и проверку
Атлетики при опрокидывании объекта. Урон не уменьшается. Значение снижается
на 1 в конце собственного хода. Испуг сам по себе не означает бегство.
Старые бои получают недостающие Запугивание/Волю из листа героя и авторского
учебного профиля NPC при следующем запросе; перезапуск боя не нужен.

Источники: [Demoralize, Player Core p. 240](https://2e.aonprd.com/Actions.aspx?ID=2395),
[Frightened, Player Core p. 444](https://2e.aonprd.com/Conditions.aspx?ID=76).
Уведомление ORC: `src/iirpg/rules/character-ORC-NOTICE.md`.

## Проверка кнопок и обсуждение

В игровом экране кнопки действий героя, включая конец хода, создают намерение
с `review: true` и `requested_action`. Текстовый ввод также использует
`review: true`: даже точная команда сначала получает предложение ИИ.
Начало учебного боя — настройка сцены. NPC уже выбирает действие через свой
контекст. Низкоуровневые команды движка и ручное решение ведущего сохранены
для тестов, автоматизации и отладки; ИИ не подменяет их проверку правил.

В поле «Обсуждение» выбирается новое действие либо продолжение сохранённого
намерения. Последнее ожидающее намерение активного героя выбирается
автоматически. `clarify_intent` принимает `intent_id`, `text` и при необходимости
выбранную цель/клетку. Уточнение сохраняет сообщение, удаляет старое
`analysis`, не расходует действия и запускает новый разбор в интерфейсе.
Без нового предложения подтвердить действие нельзя. Смена ревизии защищает
от ответа ИИ на уже уточнённый замысел. История `messages` привязана к одному
намерению и включает сообщения игрока и ответы ведущего; перезагрузка её
сохраняет. Контекст содержит именно это обсуждение, без переписки других
намерений или комнат. Ограничения: 16 сообщений и 6000 байт текста, с резервом
на ответ модели; при достижении лимита нужно создать новое намерение.

Предложение содержит `targeting`: режим `self`, `cell` или `single`, тип цели
и явные идентификаторы/позицию. Деморализация имеет `max_targets: 1` и таблицу
всех четырёх исходов. Её критпровал совпадает с провалом, дополнительных
последствий правила не вводят. Показ описания исходов в старом бою не меняет
его сохранённых механических параметров.

Для будущих площадных умений расширение `targeting` должно задавать `mode: area`,
`shape` (burst/cone/line/emanation), `origin`, `direction`, `size_feet` и фильтр
целей из конфигурации умения. Движок рассчитывает клетки, преграды и всех
затронутых существ (включая союзников, если так требует эффект), показывает
предпросмотр и отдельно разрешает проверки/иммунитеты каждой цели. Модель
уточняет намерение и выбирает поддерживаемое умение, но не назначает радиус,
количество целей или урон произвольно. Исполнителя площадных умений в текущем
прототипе пока нет; обычный крик не расширяет одиночную Деморализацию.
